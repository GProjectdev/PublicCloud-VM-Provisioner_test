NodeProvision failed-launch cooldown — 2026-11-18

Observed in aws1/ap-northeast-2c
A fresh g5.xlarge Spot request repeatedly received AWS RunInstances
InsufficientInstanceCapacity. The dedicated namespace had no EC2 instance.
Provider logs contained59 scoped error lines during the recheck. The CR's
Failed state/error was rapidly overwritten by the next CreatingInstance
state, so a five-second observer could miss the actual capacity error.
This was genuine AWS supply failure, not evidence of a quota or IAM failure.

Cause
internal/controller/ml/nodeprovision_controller.go returned RequeueAfter=1min
from failNodeProvision, but the status write itself enqueued another reconcile.
The Failed branch immediately reset Phase="", generating another status event
and launching again before the intended minute had elapsed.

Minimal change
The existing Failed branch now uses persisted status.lastUpdated to wait for
the existing requeueFailed interval before clearing the failure. Repeated
status-watch events preserve the original message/timestamp. Missing historical
timestamps are initialized once without erasing the error. A fresh status is
rechecked before retry. Deletion still precedes this phase switch, so normal
teardown is not held by the cooldown. No CRD, market policy, VM type selection,
AWS retry algorithm or finalizer bypass was introduced.
